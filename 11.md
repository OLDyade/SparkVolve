# SparkVolve

## Evolve the Harness, Not the Model.

Keep model weights fixed. Let the harness evolve through real tasks.

**One-line positioning:** A plugin-based harness evolution framework: agents use real task feedback to autonomously reshape their capability structure and turn useful improvements into reusable plugins.

The defining idea goes beyond an agent that becomes smarter with use:

> We used to equip agents with capabilities. Now agents can decide which capabilities they need, which to change, and which to create.

## Three core designs

### 1. Plugins are the genes of evolution: from manual assembly to autonomous restructuring

The evolution space spans plugin configuration, code implementation, and composition topology, extending beyond Prompt and Skills optimization.

Agents can enable, disable, tune, replace, compose, and author plugins.

This is the central technical innovation to investigate.

### 2. Evolution is a plugin: equip an existing harness with the ability to evolve

Build on DSH's native plugin system to assemble the optimizer, experiment control, and execution verification within an existing environment, without rebuilding the Agent Runtime.

Give existing harnesses the ability to evolve.

This is the product innovation that makes the approach useful to an open-source ecosystem.

### 3. Evolution results are plugins: from benchmark scores to installable capabilities

Autonomously identify problems, modify plugins, and verify improvements. Deliver an installable Bundle, candidate lineage, and reproducible experiments alongside the benchmark result.

Make the benefits of an evolution run directly reusable by other developers.

This is the delivery innovation that takes the project beyond a research prototype displaying optimization curves.

## Core guidance and design responsibility

The core ideas above define the project's direction. Their original Chinese wording is preserved in the [Chinese README](README.zh-CN.md). The following six principles are explicit, open-ended guidance, not an exhaustive requirements list. They leave room for better technical designs. Record subsequent guidance and explicitly discuss conflicts and the reasons for revisions.

| Non-negotiable principle | Typical deviation |
|---|---|
| 1. Plugins are the basic unit of evolution | Only editing Prompts or Skills, with no evolution of plugin implementation, configuration, or composition |
| 2. Build on the native DSH plugin ecosystem | Rebuilding an independent Agent Runtime and using DSH only as a wrapper |
| 3. Close a genuinely autonomous evolution loop | Repeatedly invoking a benchmark or hardcoding the optimizer's strategy in advance |
| 4. Use independent, credible experimental validation | Changing grading rules, leaking answers, cherry-picking tasks, or claiming success from one score increase |
| 5. Make evolution results reusable | Producing only a run directory or configuration that cannot be installed as a capability Bundle |
| 6. Put the general framework first; Excel is the first domain | Hardcoding SpreadsheetBench logic so that each new task requires rebuilding the evolution system |

The user sets direction, goals, and key decisions. The implementing agent proactively completes ecosystem research, architecture, interfaces, search mechanisms, experimental protocols, reliable execution, and delivery details, then reviews them against actual evidence. Unmentioned requirements still require technical judgment. Verify uncertain or potentially outdated mechanisms first; explain any conflict with the core ideas and the resulting tradeoffs.

The experiment system defines data access, budgets, and evaluation rules. Within these boundaries, the optimizer uses real feedback to select problems, parents, and mutations. Design generic evolution separately from domain adapters; independently verify plugin installation, execution, and reuse.

The three designs share one loop: stages 2-4 add evolution to an existing harness; stages 5-12 use task feedback to drive autonomous plugin restructuring; stage 13 delivers validated capabilities and reusable assets for subsequent evolution.
