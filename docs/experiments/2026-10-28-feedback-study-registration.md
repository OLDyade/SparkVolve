# What Task Feedback Can Bring to the Same Optimizer

This real-model experiment will compare the Harness generated by the same frozen G under two host feedback protocols. The goal is to observe autonomous mutation behavior, independent task quality, and actual cost, filling in questions that deterministic container acceptance cannot answer. **This document is written before model execution; the actual contract, image, source code, and build identity are frozen by the registration record generated by the driver. No results are reported before the terminal state is recorded.**

This is a limited descriptive study. It does not replace the [larger-scope E/B/R study design](../research/2026-10-28-feedback-causal-protocol.md), nor does it use winning or positive returns as an acceptance criterion.

## Fixed Objects and the Sole Comparison Variable

| Object            | Registration Definition                                                                                                 |
| --------------- | -------------------------------------------------------------------------------------------------------- |
| Optimizer G        | The same source code, lockfile, build artifacts, and native assembly of `optimizers/evidence-driven`; the two groups have identical prompt instructions and tools              |
| Initial Harness H0 | The same frozen Bundle of `examples/spreadsheet/seed`; both groups and the independent baseline reuse the original build artifacts                              |
| Model            | Venus `deepseek/deepseek-v4.1-flash-1017`, thinking off for both G/H, single maximum output 32768; the full contract records the model configuration |
| Full arm         | Authorized task inputs, source code, build, assembly, execution traces, delivery, scoring; `seed-only + full`                                 |
| Mechanical arm   | Authorized task inputs, source code, build, and native assembly; hidden task execution feedback and champion selection; `seed-only + mechanical`                 |
| Common mutation scope    | Enable, disable, tune, replace, combine, and create plugins; each mutation forks from H0, and cross-plugin coordinated modifications are allowed                         |
| Common boundaries        | Fixed tasks, model, scoring, budget, isolation, and build; task-specific special-casing, pre-written answers, guessed post-processing, and evaluation modification are prohibited                     |
| Common closures        | Research asset library, behavior probes, researcher domain QA; native assembly QA is retained                                                    |

G's general instructions specify the two feedback protocols, the raw input entry point, and the semantics of `candidate.settled`. These instructions are verbatim identical in both groups, preventing the mechanical group from stalling while waiting for events that do not exist. The optimizer chooses the mutation mechanism itself; the driver does not generate modification plans, formulas, or remediation procedures.

## Data, Repeats, and Execution Limits

All four families of the published `examples/spreadsheet/research.py` are used: normalized profit, weighted combination, debt rollover, and scenario valuation. Search uses development, and independent evaluation uses validation. The generator, original scorer, and the digest of each input/scoring directory enter the contract.

These families have been used previously in this project; validation changes the values within the same families and does not represent unknown templates, cross-domain transfer, or official SpreadsheetBench results. Scoring materials are used only by the independent evaluation process; the optimizer does not receive validation inputs, deliveries, or scores.

```text
Same G, H0, model, and search tasks
       │
       ├─ Paired block 0: Full-0 ↔ Mechanical-0
       │                 │
       │          Each arm: H0 + at most 2 mutations
       │                 │
       │          Common host rules select frozen H*
       │                 │
       │          Each independently evaluates 4 tasks
       │
       └─ Paired block 1: Mechanical-1 ↔ Full-1
                         │
                  Fresh search directory and session
                  Same budget, independent artifacts and scoring

Common H0 ── independent validation 4 tasks × 2 times
                         │
               Per-search mean + paired difference + full cost
```

| Budget Item           |                          Limit |
| ---------------- | ----------------------------: |
| Independent searches         |               2 arms × 2 times = 4 |
| Candidates per search     |           H0 + 2 new mutations = 3 |
| Search task executions     | 4 searches × 3 candidates × 4 tasks = 48 |
| Independent evaluation of selected H* |          4 searches × 4 tasks = 16 |
| Independent evaluation of common H0 |               4 tasks × 2 times = 8 |
| Total task executions     |                            72 |
| Optimizer time allocation   |      4 times × 1200 seconds = 4800 seconds |
| Search instance concurrency     |                 At most 2 per block |

The above does not include builds, assembly QA, independent scoring, or G's own request counts. It defines identical allocation limits and does not claim identical actual tokens, costs, or wall-clock time. Insufficient candidates, early termination, build failures, and service failures are all retained; no resampling, no retries, and no reordering based on results. On ordinary quality ties, H0 is retained, and H* is selected according to the host's original rules; no capability package is automatically published or promoted.

The order of paired blocks is determined before the run: rotated by repeat number according to the registered arm order, with the two arms corresponding to AB/BA. The same concurrency limit is used within a block; the next block starts after the previous block reaches its terminal state. Both planned and actual dispatch events are saved. Under concurrency, AB/BA refers to enqueue order; the actual order of container preparation and the first model request is determined by events, and strictly synchronized starts are not promised. This avoids binding a feedback mode entirely to an exclusive time slot, but it still cannot eliminate vendor load, caching, and shared host resource noise.

## Analysis and Failure Handling

- **The statistical unit is a complete independent search, with only 2 per arm.** The 4 validation tasks per artifact are repeated measures; the 8 task-instances are not interpreted as 8 independent evolutions. No significance chasing, and no conclusions drawn from resampled results.
- Report the selected version, actual code/assembly mutations, independent mean, and failures for each search. Full−Mechanical is paired by the same repeat number; H*−H0 uses the common independent baseline, retaining the correlation caused by the shared baseline.
- Raw per-task scores and the full denominator are retained. Terminated failures are counted at the registered failure value; unobserved tasks are explicitly `null` and must not be passed off as execution results.
- Report costs stratified by optimizer, task, build/QA, independent scoring, and baseline. Missing usage, unknown costs, and empty ledgers are explicitly presented; the sum of request durations does not equal wall-clock time.
- After the terminal state, review mechanisms based on actual calls, inputs, and deliveries: autonomously created tools or plugins must be checked against actual assembly and invocation; self-filled checks, successful tool registration, and a single high score are all insufficient to prove general capability.
- Both positive and negative results are retained, and artifacts undergo installation acceptance against the same real build. Engineering acceptance is marked as passed only when the code runs and the evidence is closed; quality conclusions are reported separately.
