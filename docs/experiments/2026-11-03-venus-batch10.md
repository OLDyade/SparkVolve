# Venus continuation with a shared task limit

The official DeepSeek mixed36 attempt ended after upstream 502, 429 and 402 responses. Its three search jobs failed before independent assessment. Partial development scores do not establish a method ranking. Original task evidence, request accounting and the recovered study report remain in the original local attempt.

The operator authorized a new, separate Venus attempt:

| Model | `venus / deepseek/deepseek-v4-flash-0731` |

All arms share the same task capacity. Development and independent validation use the controller's batch barrier; installed tests already use batch barriers. Probes run through the same controller pump between candidate evaluations. Serial arm execution introduces temporal ordering as a limitation and is recorded in the new registration. Results are not pooled with the official-provider attempt.

Two observed host defects were addressed before this continuation:

- A search failure could detach its observer while the optimizer kept making requests. A failed study job now reclaims its registered child resources before becoming terminal. Cleanup failures remain explicit and cannot trigger a new task attempt.
- Cleanup after a completed study could overwrite the operational error with a cancellation-state error. Terminal reclamation now preserves the original completed study state, failed jobs and conclusion, and records a separate reclamation receipt.

Regression coverage exercises batch barriers with a deliberately blocked grade, exact-once restart behavior, frozen cross-split concurrency, serial comparison dispatch, failed-job optimizer cleanup, and terminal reclamation without changing study conclusions. The native DSH suite also passes.

A fresh native DSH health check accepted the exact Venus model and output ceiling, executed a tool and replayed its result: two adapter attempts, two results, zero failed or unfinished requests. This confirms connectivity and tool replay at the time of the check; the research result still requires the full registered experiment.

## Evaluator resource failure and supplemental evidence

The attempt settled with three failed jobs. Single-plugin search selected no eligible candidate. Prompt and open-plugins selected H2, but independent validation each lost the `Debugging-10_04` grade when the official evaluator exceeded its 4 GiB container memory limit. Docker OOM events and SIGKILL logs corroborated the infrastructure failure. The executor deliveries remained available.

Each unchanged delivery was graded once more in a separate, registered 16 GiB container, serially, with the original evaluator image, command, timeout and read-only inputs. Both grades were 0.049. The original failed reports remain unchanged. Supplemental full-denominator validation means were 0.34917 for Prompt (four execution failures out of ten) and 0.51691 for open-plugins (one execution failure out of ten). These are descriptive pilot results, not a completed three-arm comparison or evidence of installed-package reuse. H0 validation and installed testing had not started when the coordinator stopped.

New contracts can explicitly set `evaluator.memoryMiB` and `evaluator.concurrency`, independently of executor resources. Absent overrides retain the experiment isolation memory and task concurrency. The controller and installed-package driver share this policy. Waiting graders retain their original task slots; the task batch barrier still includes grading, and grader concurrency cannot exceed the task limit. A failed grade releases its slot without resubmitting the task. Existing registered attempts must retain their original specifications; supplemental work records the resource change separately.


## November 4: reasoning contract correction

Supplemental H0 validation subsequently completed with six scored tasks and four execution failures out of ten, for a full-denominator mean of 0.3885. Four failures exceeded the registered limit of two, so selection, original-package installation and the 14-task test did not proceed. All four executions exited with code 137 near the 900-second deadline; Docker reported `OOMKilled=false`. This does not establish an upstream service failure.

A protocol audit found that the Venus configuration used the Qwen thinking format. The native adapter therefore sent `enable_thinking: false`, whereas DeepSeek requires `thinking: {type: "disabled"}`. Recorded assistant blocks from each of the four failed H0 tasks contained substantial reasoning despite the requested off setting. The old attempt cannot establish a thinking-off comparison. The configuration error is confirmed; its exact contribution to task quality and deadline failures remains unmeasured.

The Venus patch now selects the native adapter's `deepseek` format. A native regression test checks the actual HTTP body for `thinking.type=disabled` and the absence of Qwen and reasoning-effort fields across a tool round trip. It fails with the former configuration and passes with the correction. A separately registered real Venus arithmetic probe on November 4 completed two requests and one tool round trip, with zero reasoning output, 96 output tokens and about 4.71 seconds of summed request duration. This proves the corrected protocol for that probe, not benchmark improvement.

New SpreadsheetBench2 registrations also explicitly allocate 16 GiB and one concurrent official evaluator; executor concurrency remains independently registered. Any subsequent full comparison uses a fresh registration and unchanged seed sources, model, data membership and quality rules. Original reports and supplemental evidence stay frozen and separate; no old candidate score or failed task is repaired by rerunning it.
