### The One Research Mainline to Focus on Next

```text
Unified-configuration real startup entry point
          ↓
Pre-register a discriminative task set, freeze H0 / model config / judge / budget
          ↓
Full plugin mutation  vs  Prompt/Skill restricted mutation  vs  single-plugin restricted mutation
          ↓
Multiple independent searches → freeze candidates → independent paired execution → install and reuse the same original bundle
          ↓
Explain mechanism changes, real calls, gain variance, and cost → then expand to new domains or Spark models
```

This is a research priority order, not a started experiment or a proven gain. The specific number of repetitions and budget should be determined before the run based on available resources, the effect to be tested, and prior variance, not by picking samples afterward. All arms share the starting point, task permissions, model config, tool materials, and cost accounting, changing only the authorized mutation space; quality uses the full denominator, with failures and costs listed separately. If random mutation is added, define a reproducible and buildable sampling distribution, avoiding manufacturing a weak baseline with large amounts of random code that is bound to fail.

Fixing only the model name cannot guarantee fixed server-side weights; the current official service uses an alias, and reports retain the identity returned by the request and this limitation. Installation success, tools appearing in the Schema, tools actually being called, and business benefit are each evidenced separately. Manually repaired derived bundles and autonomously generated original bundles continue to be kept separate.
